RULING 16: THE MCT MASTER STATES ITSELF AT START.
A missing MCT master has been invisible. connection_builder.load_mct_data returns
an empty dict when the file is not there, without a message, and lookup_mct then
cascades every airport to the flat default, so a server without the master builds
every connection on 90 minutes. That changes which connections are feasible, which
moves route_qsi's scores, which moves route_forecast.dest_metro_share, which moves
the forecast on any multi-airport metro. Nothing on either screen says so.

This matters beyond the laptop build, which is where it was found. Z: is per logon
and invisible in ssh sessions, and config._resolve_egnyte_root falls back to the
nominal Z: path when it finds no marker folder, so a server started over ssh has
been resolving MCT_MASTER to a path that does not exist. Whether the workstation
portal has ever been started that way is not knowable from a code read. The next
restart answers it.

  app/connection_builder.py  mct_report() resolves through config exactly as the
                             live callers do, and returns path, exists, rows, error.
  app/cortex_app.py          the startup event prints the row count and the path, or
                             names the reason it did not load and states the
                             consequence; stand mode (AVIA_STAND_MODE) raises rather
                             than start, so the stand never demonstrates a silent
                             difference from the live tool.
  app/test_mct_report.py     holds missing, unusable and loaded apart, because they
                             are three different faults: 14 checks, 0 failed.

Verified here: both modules compile and the 14 checks pass against a workbook
written for the test. The four inline startup lines cannot run without the server's
dependencies, so they are proven by compile and by reading. The first restart is
their real test, and it is the same restart that picks up the Postmark variables.

THE WIRING FAULT IS FIXED IN CODE AND IS NOT YET MEASURED

app/bt2_capture_core.py is the one implementation the 12 August commit message asked for. load_legs,
components and cap_from moved out of bt2/bt2_capture.py into app/, and both chains now import them,
which is John's ruling of 9 August applied to the three inputs it was not applied to.

app/route_context.py no longer takes capa, qcx or legs_n from the engine payload. capture_inputs
builds all three from the store with the training implementation, at the training's own month label
and block time. A single-week OAG label is REFUSED BY NAME rather than allowed through: training
read a month and took the week of the 15th to the 21st, and handing load_legs a label like
"2026-05-25" would build the date window "2026-05-25-15", which is not a date, and return no legs.
A route with no legs reads as a route with no competition and would score a capa of 1.0.

Two quantities are called qcx and they are not the same. Inside cap_from it carries the 0.20
one-stop factor and covers one direction. The MODEL FEATURE sums both directions and carries no such
factor. Each is now built by its own named function and neither is derived from the other, because
sharing a name is most of how this went wrong.

app/bt2_input_check.py is the test bt2_wiring_test.py could not be. It takes routes the training
chain has already scored, asks the LIVE path for the same three numbers, and compares against
capture_L.csv. A pass is a difference of zero on all three. The tolerance is floating point and is
not to be widened: the two chains now run the same code, so any real difference is a difference in
the arguments, and the arguments are the finding. RUN IT BEFORE ANYTHING ELSE.

THE SCENARIO RUNNER

app/scenario_runner.py generalises app/econ_baseline.py. A cases file in, a table out, no Python
written by the tester. Cases may be JSON or CSV and carry route, carrier, aircraft, seats,
frequency, forecast year, growth path, departure time, partner carriers, split_floor, plan cap,
season and curfews. Every figure comes from cortex_app.calibrated_forecast, so a scenario run and the
portal answer the same question with the same code; if the two ever disagree that is a defect in the
runner.

  Everything is reported TWO-WAY, and every doubled column says so in its name. Mixing the engine's
  each-way convention with BT2's both-directions seats_ly cost an afternoon on 9 August.

  demand_lf and plan_lf_achieved are SEPARATE COLUMNS. The first is demand over seats and answers
  whether the demand is there to fill the aeroplane; the second is carried over seats, is capped,
  and can only ever be the lower. Reading one for the other is the capped-against-uncapped error
  that invalidated a comparison quoted for a week.

  It FAILS LOUDLY on a payload key it does not recognise, REFUSES TO WRITE a table in which any
  case errored, and REFUSES TO RUN without AVIA_FREQ_SENSITIVE unless the cases file says plainly
  that it means to. With that switch off a frequency ladder returns the same demand at 3x and at
  14x and only the load factor moves, which a tester would not necessarily notice.

  A misspelled setting is rejected by name rather than ignored, because a run carrying a setting the
  tester believes is on is worse than a run that stops.

app/cases_sjc_tpe.json carries sixteen cases: China Airlines, EVA, Starlux, United and Delta on
SJC-TPE at four to seven weekly across 2027 and 2028, one case with the connectivity floor on as it
ships, SFO-TPE as a served control, and SJC-LHR and GOA-JFK as other routes. Seat counts are the
carriers' own configurations measured from OAG 2025 by capacity_frame, not the generic type table,
which overstates capacity by 8 to 13% on these carriers. Growth is the post-recovery path at 7% a
year, per John's ruling that the default taper measures a 20.00% CAGR, which is the clamp ceiling
and a recovery burst.

# PINNED, and it is not housekeeping. airportsdata supplies every coordinate the engine uses, so a
# release that corrects one airport's position shifts a great-circle distance, which shifts the
# circuity screen, which can add or drop a competing hub, which moves the QSI share. Measured on
# 11 August 2026: the same commit reading the same stores returned qsi_share 0.2510 on 20260315 and
# 0.2513 on 20260803. That is small and it is a forecast changing because a library was updated,
# which is not acceptable in a number a client is shown. The version is an INPUT and belongs beside
# the store vintage. bt2/coord_check.py names which airport moved when two machines disagree.

# PINNED FOR THE SAME REASON AS airportsdata, and it was not listed here at all until 13 August
# 2026, which is why it came to be installed by hand on the workstation and drifted. BT2's
# calibrated figure is the one on the website, and it MOVES WITH THIS VERSION.
#
# Measured 13 August 2026, identical artefacts, identical sample of 6,524, identical config, the
# only difference being the library:
#
#            calibrated +-20%   +-10%   tier A   portfolios of 20   blind route
#   1.7.2          84.6%        72.4%    87.3%        94.7%            60.9%
#   1.9.0          83.2%        70.0%    88.2%        93.2%            60.9%
#
# 1.7.2 reproduces the 9 August figures EXACTLY on every line. The blind route figure is identical
# on both because its config is regularised, minleaf=60 and l2=5.0; the calibrated config runs
# minleaf=5 with no l2 and is essentially unregularised, so it is sensitive to how a library breaks
# a tie. A published claim that moves 2.4 points with a package install is not a claim.
#
# WHICH VERSION TO PIN, and the first answer here was wrong. 1.7.2 was pinned on the grounds that it
# is what the published figures were measured on. It is, but so is airportsdata 20260315, which this
# file does NOT declare: the airportsdata pin above was set to 20260803 on 11 August, two days AFTER
# the 9 August claim set was produced. Measured 13 August: the Dev PC carries 20260315 with sklearn
# 1.7.2 and reproduces 9 August exactly; the workstation carries the pinned 20260803 with sklearn
# 1.9.0 and does not. So the published figures describe an environment the repo has never declared,
# and chasing them would mean unpinning airportsdata, which would undo a deliberate decision.
#
# PINNED TO THE RUN HOST instead. The workstation is where clients are served from, cortex_app reads
# airportsdata 20260803 live, and bt2_g12_exp.metro_map builds the sister feature from the same
# library, so the model's features and the engine's geography should come from ONE release. That
# makes 20260803 the right airportsdata and the workstation's sklearn the one to standardise on.
#
# CONSEQUENCE, and it is not optional: the claim set must be RE-MEASURED once on this declared pair
# and the site restated if the figures move. The 9 August numbers then become history produced on an
# undeclared environment, which is what they always were. bt2_claimset stamps python, sklearn,
# numpy, scipy AND airportsdata on every run so this cannot recur silently.
